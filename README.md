## Функції модуля

| Функція | Призначення | Приклад |
| --- | --- | --- |
| `is_palindrome(s: str) -> bool` | Перевіряє, чи однаково читається рядок в обох напрямках | `is_palindrome("level")` → `True` |
| `reverse_words(s: str) -> str` | Змінює порядок слів на зворотний | `reverse_words("Я вивчаю Python")` → `"Python вивчаю Я"` |

`is_palindrome` враховує регістр, пробіли та розділові знаки.
Наприклад, `is_palindrome("Level")` повертає `False`. Порожній рядок і рядок
з одного символу вважаються паліндромами.

`reverse_words` розділяє слова за пробільними символами, зокрема пробілами,
табуляцією та перенесеннями рядка. У результаті між словами залишається
один пробіл; порожній рядок або рядок лише з пробільних символів дає `""`.

## Локальний запуск тестів

Для локального запуску рекомендовано Python 3.12.
CI перевіряє тести на Python 3.10, 3.11 і 3.12.
Docker-образ використовує Python 3.12.

Склонуйте репозиторій і перейдіть до його папки:

```powershell
git clone https://github.com/andr77eeeew/ci-lab-string-utils.git
cd ci-lab-string-utils
```

Якщо репозиторій уже є на комп'ютері, відкрийте його папку.
У Windows PowerShell створіть віртуальне середовище, установіть залежності
та запустіть тести:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest -v
```

Набір містить **9 тестів**: перевірки паліндромів, українських символів,
регістру, порожнього рядка, одного символу та зміни порядку слів
із різними пробільними символами. Очікуваний підсумок — `9 passed`.

## Запуск через Docker

Для Windows установіть і запустіть Docker Desktop із Linux-контейнерами.
Для завантаження образу потрібне з'єднання з інтернетом.

Після успішної публікації образу завантажте його з GHCR:

```powershell
docker pull ghcr.io/andr77eeeew/ci-lab-app:latest
```

Запустіть автоматичні тести всередині контейнера:

```powershell
docker run --rm ghcr.io/andr77eeeew/ci-lab-app:latest
```

Очікуваний результат — `9 passed`. Після завершення тестів контейнер
завершує роботу, а параметр `--rm` видаляє його. Образ залишається
на комп'ютері для наступних запусків.

Публічний пакет GHCR можна завантажити без авторизації. Якщо пакет
приватний, для завантаження потрібна авторизація з доступом до нього.

### Збирання образу з локальних файлів

Виконайте в корені репозиторію, де розташований Dockerfile:

```powershell
docker build -t ci-lab-app:local .
docker run --rm ci-lab-app:local
```

Dockerfile використовує базовий образ `python:3.12-slim`, установлює
залежності, копіює проєкт і задає команду `pytest -v`.
Файл `.dockerignore` виключає з контексту збірки Git-метадані,
локальні віртуальні середовища та кеші Python і pytest.

## Додатковий крок 16 ПЗ 1: матриця версій Python

У GitHub Actions налаштовано матрицю Python 3.10, 3.11 і 3.12.
Для кожної версії створюється окреме середовище, встановлюються
залежності та запускається той самий набір із дев’яти тестів.

Параметр `fail-fast: false` дозволяє отримати результати перевірки
для всіх версій, навіть якщо одна з них завершиться помилкою.

Завдання `build-and-push-image` залежить від `build-and-test`
і виконується після успішного завершення всіх перевірок матриці
під час push у main.

## Запуск через Docker Compose

Додатковий крок 16 ПЗ 2 описує запуск тестового контейнера через Docker Compose.
Для Windows потрібен запущений Docker Desktop із Linux-контейнерами.
Усі команди нижче виконуйте в корені репозиторію.

Створіть поруч із Dockerfile файл `docker-compose.yml` із таким вмістом:

```yaml
services:
  tests:
    image: ghcr.io/andr77eeeew/ci-lab-app:latest
    command: ["pytest", "-v"]
    restart: "no"
```

Сервіс `tests` використовує готовий образ із GHCR, запускає `pytest -v`
і завершує роботу після тестів без автоматичного перезапуску.

Перевірте доступність Compose та конфігурацію:

```powershell
docker compose version
docker compose config
```

Завантажте актуальний образ і запустіть тести:

```powershell
docker compose pull
docker compose up --exit-code-from tests
$LASTEXITCODE
```

Очікуваний результат — `9 passed`, завершення контейнера з кодом `0`
та значення `$LASTEXITCODE`, що дорівнює `0`. Перевіряйте `$LASTEXITCODE`
одразу після завершення команди запуску.

Параметр `--exit-code-from tests` повертає код завершення тестового сервісу.
Це дає змогу відрізнити успішний запуск тестів від запуску з помилкою.
Звичайна команда `docker compose up` також запускає сервіс і показує його журнал.

Після перевірки приберіть створені контейнер і мережу Compose:

```powershell
docker compose down
```

## Автоматизація в GitHub Actions

Workflow `.github/workflows/ci.yml` запускається після `push` у `main`
і для Pull Request, спрямованих у `main`.

| Завдання | Дії | Умова запуску |
| --- | --- | --- |
| `build-and-test` | Отримує код, налаштовує Python 3.12, установлює залежності та запускає `python -m pytest -v` | `push` у `main` або Pull Request до `main` |
| `build-and-push-image` | Збирає Docker-образ і публікує його в GHCR | Лише подія `push`, після успішного `build-and-test` |

Залежність `needs: build-and-test` запобігає публікації образу, якщо тести
не пройшли. Під час перевірки Pull Request завдання публікації пропускається.

Для входу в GHCR workflow використовує автоматично наданий
`secrets.GITHUB_TOKEN` із дозволом `packages: write`.
Ручне створення цього секрету не потрібне.

Образ публікується з двома тегами:

- `ghcr.io/andr77eeeew/ci-lab-app:latest` — оновлюється після успішної публікації;
- `ghcr.io/andr77eeeew/ci-lab-app:<SHA>` — відповідає повному хешу коміту,
  із якого зібрано образ.

## Перевірка результатів

- На вкладці **Actions** відкрийте останній запуск після `push` у `main`
  та перевірте успішне завершення обох завдань.
- У розділі **Packages** перевірте образ `ci-lab-app` і його теги.
- Завантажте опублікований образ командою `docker pull` і перевірте
  проходження тестів командою `docker run`.

- Для перевірки Compose виконайте `docker compose up --exit-code-from tests`
  та переконайтеся, що всі тести пройшли з кодом завершення `0`.
